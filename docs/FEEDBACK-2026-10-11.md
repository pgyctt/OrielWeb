# 下游反馈：物料塔控制系统迁移到 net10 + OrielWeb（0.3.1）

> 来源：一个真实工业上位机（WinForms 无边框窗体 + WebView2 + 自研 postMessage 桥 → OrielWeb）的完整迁移。
> 43 条 IPC 命令、1 万行前端、自包含发布。迁移已完成并在真机跑通，下面是**下游视角**的需求清单。
>
> 结论一句话：**0.3.1 足够承载一个真实应用，但有三处缺口迫使下游做了带损失的降级，另有六处能力缺口需要各自打补丁。**
> 每条都附了本仓库的 `文件:行` 证据与下游当时的替代做法。
>
> 环境：Windows 11 / .NET SDK 10.0.401 / OrielWeb 0.3.1（net10.0）/ 自包含非 AOT 发布。
> 日期：2026-10-11。

---

## 零、先说站得住的部分

不吹，但这几条是迁移能一次跑通的直接原因，改坏它们会伤到下游：

- **`IpcRejected`（0.3.1 新增）正中要害**。下游的现场问题是"页面按钮点了没反应"，
  而这类故障的第一嫌疑就是被门禁拦下。有它在，宿主终于能看见 `Source`/`Token`/`Command` 三层拒绝。
  迁移后这条是唯一的 IPC 故障观测入口。
- **内嵌资源不落盘 + `oriel://` 自定义 scheme**。下游是"解压即用"的产线部署形态，
  不写盘这一点顺带消灭了"启动时递归清空目录""删错路径"这一整类风险。
- **DPI 处理是对的**。`Win32WindowHost` 全程 `GetDpiForWindow` + `LogicalPixels.ToPhysical`
  （`Platform/Windows/Win32WindowHost.cs:389,778-780,1436-1437`），
  0.3.1 又把窗口尺寸统一成逻辑像素——下游担心的"非 100% 缩放布局错位"因此没有发生。
- **`onCreated` 之外的事件面很完整**。`Closing` / `MaximizedChanged` / `MessageReceived` /
  `NavigationCompleted` / `ConsoleMessage` 足够搭出"首帧闸门 + 关闭入托 + 窗口状态推送"三件套。

## 一、P0：阻断级（导致下游只能带损失降级）

### P0-1　页面缩放开关缺失 —— 下游唯一**完全没有替代方案**的缺口

**证据**：全库零命中。`grep -rn "IsZoomControlEnabled\|IsPinchZoomEnabled\|SetZoomFactor" src/` → 空。
`Platform/Windows/Win32WindowHost.cs` 里没有任何 zoom 相关代码。

**为什么是 P0**：库不暴露 WebView2 控制器、**也不暴露 HWND**，所以下游既调不到库、也设不了底层设置——
没有任何逃生口。下游是固定布局的工业界面，整屏被误缩放会导致布局错乱且无复位入口，
原实现显式关掉了 `IsZoomControlEnabled` 与 `IsPinchZoomEnabled`（现场可能是触摸屏一体机）。

**下游的降级**：退到页面侧缓解——根元素 `touch-action: pan-x pan-y`（Chromium 下排除 pinch-zoom）
+ JS 非被动监听挡 Ctrl+滚轮 / Ctrl+±。**这是已知偏差，不是等价替代**：
如果真机上捏合仍生效，只能回退到 WinForms + WebView2 宿主。

**建议 API**（跨平台抽象，三平台各自映射）：

```csharp
OrielWindowOptions.WithZoom(bool enabled);                    // 关掉 Ctrl+滚轮 / Ctrl+± / 捏合
OrielWindowOptions.WithZoomRange(double min, double max);     // 可选，给需要限制缩放的应用
```

- Windows：`CoreWebView2Settings.IsZoomControlEnabled` + `IsPinchZoomEnabled`（一对一）
- macOS：`WKWebView.allowsMagnification`（捏合）+ 拦 Ctrl+滚轮
- Linux：WebKitGTK 没有等价单开关，需要在 `WebKitSettings` / GTK 事件层挡，可能要配合页面侧

> 若认为"暴露引擎专有设置会污染跨平台抽象"，那么退一步的最低要求是：
> **给一个受控的引擎逃生口**（例如 `WithPlatformHook(object engine)` 或文档化的 `EvaluateJs` 之外的注入点），
> 让下游能自己设。现状是"既不给抽象、也不给逃生口"，这是最难受的形态。

### P0-2　单实例判定太晚，下游必须自己再造一道锁

**证据**：`App/SingleInstanceGuard.cs:17` 是 `internal static class`，全类无公开成员；
判定发生在 `App/OrielApp.cs:403`，即 **`Run()` 的第一件事**。

**为什么是 P0**：`Run()` 之前，宿主必须先把配置、数据库、设备连接装配起来。
下游的 `AppRuntimeHost.Rebuild()` 会打开 SQLite 并 `StartDevice()` 起 Modbus 轮询——
于是"第二个实例"在被库识别并退出**之前**，已经连上了同一台 PLC、并向同一个库写任务/报警记录。

**实测证据**（迁移后的日志，加前置锁之前）：

```
08:25:18.597 [INFO] 物料塔控制系统启动          ← 第二实例
08:25:18.599 [INFO] [启动] 配置与服务初始化完成
08:25:18.630 [INFO] [启动] 检测到第二实例，已前置现有窗口。
```

**下游的降级**：自己加了一道进程级命名互斥量（`SingleInstanceProbe`），
在装配运行时**之前**抢锁；抢不到就跳过 `AppRuntimeHost.Rebuild`，但仍走库的 `Run()`
（让库负责"通知首实例前置激活并静默退出"）。分工变成：**下游管要不要装配运行时，库管激活首实例**。
能用，但这是库本该提供的分流点。

**建议 API**（任一即可，成本都很低）：

```csharp
// 方案 A：把已有的 internal 探针开成公开只读查询（改动最小）
public static bool SingleInstanceGuard.IsAlreadyRunning(string id);

// 方案 B：在 Build() 之后、Run() 之前就能问
OrielApp app = builder.Build();
if (app.IsSecondaryInstance) { /* 跳过昂贵装配 */ }
app.Run();
```

**顺带一条**：`SingleInstance` 不传第二实例的命令行参数，`onActivate` 只给首实例的窗口。
"用命令行让已运行的程序打开某个页面"这类需求目前做不了。建议 `onActivate(WebviewWindow?, string[]? secondaryArgs)`。

### P0-3　命令异常在 Release 下是黑洞：宿主侧完全没有观测点

**证据**（两条叠加，缺一不可）：

1. `Ipc/OrielCommandDispatcher.cs:159` 唯一的宿主侧留痕是 `Debug.WriteLine`。
   而 `Debug.WriteLine` 带 `[Conditional("DEBUG")]`，**条件是在"调用方所在程序集"的编译期求值的**——
   库以 Release 发布，所以这些调用在 IL 里根本不存在。
   实测扫描发布包字符串堆：`[OrielWeb]` 前缀的字符串**一个都不在**（`命令 '{name}' 执行失败（详情不透传页面）`、
   `RevealInFileManager 拒绝了不可用路径` 等全部被编译掉）。
2. `DescribeForPage` 对非 `OrielIpcException` 只回一句通用文案（这个设计下游认同，理由也认同：防 Message 泄漏内部路径）。

**为什么是 P0**：两条加起来意味着——**生产环境里命令抛异常时，页面看到"命令失败"，宿主日志里什么都没有**。
对现场排障这是致命的：下游 43 条命令里有 SQLite 事务、NPOI 解析、Modbus 通信，异常是常态。

**下游的降级**：在 `CommandBase` 基类里给**每条命令**包 try/catch 记日志再 rethrow。
能用，但等于把库该做的横切关注点抄了一遍。

**建议 API**（任一即可）：

```csharp
// 方案 A：加观测事件（与 IpcRejected 对称，下游最想要这个）
public event Action<OrielCommandInvokedEventArgs>? CommandInvoked;   // 命令名、耗时、结果、异常对象
public event Action<OrielCommandFailedEventArgs>? CommandFailed;     // 异常原样带出（只给宿主，不给页面）

// 方案 B：把"回给页面的文案"变成可替换策略（比 A 更小）
OrielAppBuilder.UseCommandErrorFormatter(Func<string, Exception, string> formatter);
```

A 与 B 不冲突：A 解决"宿主怎么知道"，B 解决"宿主能不能决定给页面多少信息"。
另外**耗时**值得带上——下游 200ms 节拍 + 43 条命令，需要知道哪条命令慢。

> 附带一条同类问题：`OrielShellLauncher` 的路径拒绝、`RevealInFileManager` 的不可用路径等
> 也都是 `Debug.WriteLine`，同样在发布包里被编译掉。**建议全库把 `Debug.WriteLine` 换成
> 一个始终存在的可订阅诊断通道**（哪怕默认无订阅者、零开销）。

## 二、P1：能力缺口（有替代，但替代都带可见损失）

### P1-1　窗口配色 / 背景色入口缺失

**证据**：全库零命中。`grep -rn "BackgroundColor\|DwmSetWindowAttribute\|DWMA_\|Mica\|Backdrop" src/` → 空。

**影响**：下游原本由宿主在 `OnPaint` 里画还原态的 1px 边框、并用窗体底色填充 WebView2 内缩区域。
现在库既无配色入口、也不给 HWND，宿主侧画不了——只能改成**页面 CSS 自绘**
（`.app-shell--restored { border: 1px solid var(--glass-edge) }`）。
功能上可接受，但两个副作用：边框从"内缩 2px"变成"紧贴屏幕边缘"，且内核就绪前的那一帧底色不受宿主控制。

**建议 API**：

```csharp
OrielWindowOptions.WithBackgroundColor(uint argb);   // 内核就绪前的窗口底色，避免白/黑闪
OrielWindowOptions.WithBorderColor(uint argb);       // 还原态外壳边框（可选）
```

只做 `WithBackgroundColor` 就能覆盖大部分场景（启动闪色是所有 webview 应用的共同问题）。

---

### P1-2　边缘缩放：内建了但不可配、未文档化

**证据**：`Platform/Windows/Win32WindowHost.cs:1303` `HitTestResizeBorder`，
`:1436-1437` 取 `GetSystemMetricsForDpi(SM_CXSIZEFRAME) + SM_CXPADDEDBORDER` ——
**厚度是系统默认值，不可配**；且 `:1306` 在 fullscreen / maximized 时直接跳过。

**影响**：下游原先是"前端边缘热区 + 2px 原生兜底"两套机制（因为窗体不预留可见边距时原生环带太窄不好抓）。
迁移后热区方案作废（没有 `win.resize` 命令、没有 HWND），**只能完全依赖库的默认厚度**。
库若不生效则没有兜底手段。另外"是否受 `WithResizable` 约束""是否仅 frameless 下启用"都没写。

**建议**：不一定要加 API，但**至少要文档化**：边缘缩放是否总启用、厚度是多少、受哪些 `With*` 影响。
若要加，`WithResizeBorderThickness(int logicalPx)` 是最小形态。

---

### P1-3　内建右键菜单只有三档，无法按目标元素条件放行

**证据**：`App/OrielContextMenuPolicy.cs` 只有 `Editing` / `Native` / `Disabled`；
`OrielWindowOptions.WithContextMenuPolicy(policy)` 无 predicate 重载。

**影响**：下游原实现是两级过滤——按**目标元素**（只对可编辑元素与选中文本放行）
+ 按**菜单项**（只保留 undo/redo/cut/copy/paste/pasteAndMatchStyle/selectAll 共 7 项，
剔除 Chromium 塞进来的"导入密码"等）。库只能取最接近的 `Editing` 档，
**丢了 undo/redo/selectAll/pasteAndMatchStyle 四项**。

**建议 API**：

```csharp
OrielWindowOptions.WithContextMenuPolicy(OrielContextMenuPolicy policy,
                                         Func<OrielContextMenuTarget, bool>? predicate);
// 或一个可取消事件
public event Action<OrielContextMenuOpeningEventArgs>? ContextMenuOpening;  // e.Handled / e.MenuItems
```

### P1-4　托盘气泡：已被试过并放弃，但下游需要"关闭入托"的可见反馈

**证据**：interop 字段都在（`Platform/Windows/Interop/Win32Native.cs:56,722-727` 的
`NIF_INFO` / `szInfo` / `szInfoTitle` / `hBalloonIcon`），但
`Platform/Windows/Win32TrayBackend.cs:239` 只用 `NIF_MESSAGE|NIF_ICON|NIF_TIP|NIF_SHOWTIP`。
`Platform/Windows/Win32ToastNotification.cs:13` 写明了原因：
> 早先走的是托盘气球（`NIF_INFO`）：既要求托盘在、实测里又根本没显示出来——换来的是能回传点击，但看不见的通知谈不上"能用"。

**所以这不是漏做，是踩过坑的取舍。** 下游接受这个判断，但要指出一个后果：
**toast 依赖 AUMID 注册、可被现场"专注助手/通知权限"关掉**，而托盘气泡不依赖这些。
下游用"关闭 = 隐藏入托"的语义，如果操作员点关闭后什么提示都没有，会以为程序被关了却还在跑 PLC 采集。

**建议**：把这条**写进 API.md / ROADMAP 的已知取舍**（现在只藏在源码注释里，下游无从得知，
是我在反射探测时才发现"没有 Balloon"）。若愿意，`OrielTray.ShowBalloon(...)` 作为 opt-in 保留
（反正 interop 已经在了），文档注明"部分 Windows 配置下可能不显示，优先用 ShowNotification"。

### P1-5　无命令调用观测（耗时 / 成功率）

**证据**：`App/OrielApp.cs` 只有两个公开事件（`:39` `IpcRejected`、`:154` `ThemeChanged`）。

**影响**：下游有 43 条命令跑在 200ms 节拍上，需要回答"哪条命令慢""哪条在失败"。
现在只能靠自己在每条命令里记日志。见 P0-3 的建议 API，一并解决。

### P1-6　`UseJsonContext` 的"必须"程度与文档不符

**证据**：`OrielAppBuilder.UseJsonContext(JsonSerializerContext)` 只有这一个重载，无 `JsonSerializerOptions` 版本。

**实际语义**（下游实测）：只有 **POCO 参数 / POCO 返回值**才真正需要它。
生成器对 `JsonElement` 参数是 `var __arg_args = args;` 直接透传整个 payload，
`JsonElement` 返回值也只需在上下文里登记这一种类型。
下游因此用"全部命令走 `JsonElement` 入参/出参 + 只登记 `JsonElement`"绕过了源生成上下文的维护负担
（同时保住了与改造前逐字节一致的响应体）。

**建议**：文档说清这个边界（"用 JsonElement 逃生口时不必把 DTO 搬进上下文"），
或补一个 `UseJsonOptions(JsonSerializerOptions)` 重载给非 AOT 场景。

## 三、P2：一致性 / 文档

### P2-1　targets 的 `LogicalName` 不归一 `%(RecursiveDir)` 的反斜杠

**证据**：`buildTransitive/OrielWeb.targets` 用
`LogicalName="$(_OrielWebAssetAssemblyName).wwwroot/%(RecursiveDir)%(Filename)%(Extension)"`，
而 `%(RecursiveDir)` 在 Windows 上带**反斜杠**。下游实测反射读出的资源名：

```
NewPwr.MTS.wwwroot/index.html                    ← 根目录文件，正常
NewPwr.MTS.wwwroot/assets\AlarmQueryPage-xxx.js  ← 子目录文件，混合分隔符
```

**为什么不算功能缺陷**：`Assets/EmbeddedAssetStore.cs:121` 读取时会归一
（`MapResourceToPath(name[prefix.Length..]).Replace('\\', '/')`），所以页面加载正常，下游实测确认。
**但与两处声明不一致**：
- README「内嵌页面资源」明写"资源名用**显式 `/` 分隔符**（`MyApp.wwwroot/assets/img/logo.svg`）"；
- 单测 `EmbeddedAssetTests` 声称"只认显式 `/` 分隔符这一种约定"。

下游在 `publish.ps1` 的自检里因此不敢把"资源名必须全用 `/`"当断言，只能降级成一条提示。

**建议**：targets 里补 `.Replace('\','/')`（与 README 的推荐写法逐字符一致），
或在 README/API.md 里如实说明"Windows 上子目录资源是混合分隔符形态，库读取时会归一"。

---

### P2-2　`onCreated` 的调用时机完全没文档化 —— 下游踩的最大的坑

**实测**：`AddWindow(configure, onCreated)` 在**配置阶段**就调用 `onCreated`（早于 `Run()`）。
此时窗口后端尚未初始化，访问 `window.App` 直接抛：

```
窗口后端尚未初始化：请在 OrielAppBuilder.Run() 之后使用窗口能力。
   at OrielWeb.WebviewWindow.get_Backend()
   at OrielWeb.WebviewWindow.get_App()
   at NewPwr.MTS.Hosting.AppHost.OnWindowCreated(...)
   at OrielWeb.OrielAppBuilder.AddWindowCore(Action`1, Action`1)
```

而 README 只说"`onCreated` 回调里拿不到 app 变量（要等 `Run()` 返回）"——
**"拿不到"和"访问即抛异常"是两回事**，前者听起来像返回 null。
下游据此把 onCreated 写成"配置 + 接线"一体的初始化函数，结果启动即崩。

**建议**：文档里明确一句——"`onCreated` 是**配置期**回调，用于在 `Run()` 之前挂事件处理器；
任何需要窗口后端的能力（`App`、`PostToUiThread`、`Show`/`Hide`、`EmitEvent`）都必须在
`Loaded` / `NavigationCompleted` 之后才能使用"。这一条能省下游半天。

---

### P2-3　`win.*` 保留前缀的范围没说明（是否含事件名）

README 说"应用自己的命令**不要用 `win.` 前缀**"，但没说 `EmitEvent` 的事件名是否同样受限。
下游把窗口状态事件命名为 `win.state.changed`，被自己的保留前缀检查拦下（下游的锅），
但根因是"事件命名空间是否也归库保留"无从判断。
（`CHANGELOG` 0.3.1 提到 `win.` 保留前缀会给出编译期**警告** `ORIELWEB101–106` 之一，
但那只覆盖命令方法，事件名不在生成器视野里。）

**建议**：文档加一句边界说明。

---

### P2-4　`With*` 方法大量无 XML 文档

`WithMaximized` / `WithFrameless` / `WithSize` / `WithHidden` / `WithResizable` / `WithDebug` 等
**没有 XML 文档注释**，用 IDE 提示或查文档会"查不到"，但它们确实存在且可用
（下游是靠反射转储 `With[A-Z][A-Za-z]{2,30}` 才确认的）。
另外反向也有坑：XML 文档里有但**不是 public** 的成员（如 `OrielCapabilityOptions.NormalizeOrigin`
是 `internal static`），照着文档调用会报 CS0117。

**建议**：给所有公开 `With*` 补一行 `<summary>`；并在 API.md 里说明"XML 文档包含 internal 成员，
不能当公开 API 用"。

---

### P2-5　首帧闸门没有一等入口

库有 `WithHidden` + `Show()`，但没有"等页面首屏渲染完成再显示"的封装。
`Loaded` 的语义是"首次导航完成"，**早于前端框架首屏渲染**，直接用会退回"白屏/半成品一闪"的观感。
下游因此仍自己实现（前端 `postMessage('ui.ready')` → 宿主 `Show()` + 8s 兜底）。

**建议**：把"首帧闸门"作为**推荐用法写进 README/API.md**（这几乎是所有 webview 应用都会遇到的第一个问题），
或提供 `OrielWindowOptions.WithShowOnPageReady(string messageName = "oriel.ready")`。

## 五、如果只做三件事

按"下游损失 ÷ 改动成本"排序：

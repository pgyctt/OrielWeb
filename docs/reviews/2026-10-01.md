**行尾约定**（`core.autocrlf` 的去留）：仓库的 `.gitattributes` 里 `* text=auto eol=lf` **已经是唯一权威**——

所以**不需要**让每个人都去关 `core.autocrlf`。本次另外做了两件事：

1. 给 `.gitattributes` 补了例外 `*.bat` / `*.cmd` → `eol=crlf`（cmd.exe 解析 LF-only 批处理在标签跳转上有兼容问题；当前仓库没有此类文件，属为将来加）。
2. 在**仓库级**配置里覆盖 `core.autocrlf=false`（本机该值来自 PortableGit 自带的系统级 `etc/gitconfig`，
   不是仓库也不是用户全局）。这只影响本机，但能消除"LF will be replaced by CRLF"这类歧义。

> 归一 LF 后曾有 5 个文件在 `git status` 里显示为已修改，而 `git diff` 说无差异——

> git 靠 stat 先判为已修改，内容比对又证明一致。对这几个文件做一次 `git add` 刷新 stat 即可
> （内容与索引相同，因此**不会暂存任何改动**，已用 `git diff --cached` 确认）。

### 4.1 【高】单实例锁把"锁文件创建失败"误判成"已有实例"，应用静默不启动

**位置**：`src/OrielWeb/App/SingleInstanceGuard.cs:31-45`，消费点 `src/OrielWeb/App/OrielApp.cs:260-273`

```csharp
catch (Exception ex) when (ex is IOException or UnauthorizedAccessException)
{
    // 锁被占用：这就是"已有实例"的正常信号，不是错误
    lockFile = null;
    return false;
}
```

**现象**：`TryAcquire` 把**任何** `IOException` / `UnauthorizedAccessException` 都当成"已有实例在跑"。但这两类异常远不止"文件被独占"一种来源——临时目录只读、磁盘满、`TMPDIR` 指向不可写位置、杀软/沙箱拦截，都会抛同样的异常。

**后果**：此时 `OrielApp.Run()` 走到

```csharp
if (!SingleInstanceGuard.TryAcquire(instanceId, out FileStream? lockFile))
{
    SingleInstanceGuard.NotifyPrimary(instanceId);
    Console.WriteLine("SINGLE-INSTANCE-SECONDARY: 已有实例，已通知并退出");
    return;   // 不进消息循环
}
```

即：**不建窗、不进消息循环、直接返回，进程以退出码 0 正常结束**，用户看到的只是"点了没反应"。而"第二个实例"这个诊断信息还被 `Console.WriteLine` 写到标准输出——`WinExe` 应用根本没有控制台，等于没有任何可见线索。

**影响**：这是典型的"最难排查的失败形态"——退出码是成功的、日志是误导的、行为是静默的。而且它在**每台机器上表现不同**（取决于临时目录权限），只在特定部署环境下复现。

**建议**：
1. 区分"锁被占用"与"锁无法创建"。`FileStream` 抛 `IOException` 时检查 `HResult`（`ERROR_SHARING_VIOLATION` 0x80070020 / `ERROR_LOCK_VIOLATION` 0x80070021）才判定为"已有实例"；其余情况应**视为可继续启动**或抛出明确异常。
2. 更稳妥的做法：锁文件先尝试以 `FileShare.None` 打开；失败后再探一次"管道能否连上首实例"（`NotifyPrimary` 已经会连），连得上才认定是第二实例，连不上则说明是权限问题，应当正常启动。
3. 无论如何，不要用 `Console.WriteLine` 做这类诊断——`WinExe` 下它是黑洞。至少写到 `Debug.WriteLine` 或应用日志。

**证据**：读码 + 调用链推演（`TryAcquire` 返回 `false` 的唯一分支即上述 catch）。

### 4.3 【中高】内嵌资源解压器会把含 `.` 的文件名静默映射成错误路径

**位置**：`src/OrielWeb/Assets/EmbeddedAssetExtractor.cs:61-70`

```csharp
var extensionIndex = resourceSuffix.LastIndexOf('.');
var stem = resourceSuffix[..extensionIndex].Replace('.', Path.DirectorySeparatorChar);
return stem + resourceSuffix[extensionIndex..];
```

**现象**：逻辑是"取最后一个 `.` 当扩展名分隔符，前面的 `.` 一律当目录分隔符"。对 `assets/img/logo.svg`（资源名 `…wwwroot.assets.img.logo.svg`）是对的，但对**文件名主干里含 `.` 的资源会算错**：

| `logo.dark.svg` | `logo.dark.svg` | `logo/dark.svg` ❌ | `logo.dark.svg` |

**为什么这不是"边缘情况"**：README 的快速开始直接教用户

```xml
<EmbeddedResource Include="wwwroot\**\*" /> <!-- 前端资源内嵌 -->
```

而任何真实前端构建产物（Vite/webpack/rollup）默认就会产出 `app.min.js`、`vendor.bundle.js`、`index.<hash>.js` 这类带点文件名。**用户照着 README 抄，就会踩中。**

**当前是否触发**：否。`samples/OrielDemo/wwwroot` 只有 `about.html`、`app.js`、`index.html`、`manual-check.html`、`manual-check.js`、`styles.css`——没有带点主干。**这是一个尚未被踩到的地雷。**

**代码自己承认了限制**（第 35 行注释："文件名主干中再含 `.` 的资源不受支持"），但：
- README **没有**写这条限制；
- 失败是**静默的**（生成错误路径），而不是**拒绝或告警**。

**建议**（任选其一，建议 1+3）：
1. 用资源的**真实元数据**而不是名字猜路径。最稳的是在 csproj 里用 `<EmbeddedResource Include="wwwroot\**\*" LogicalName="wwwroot/%(RecursiveDir)%(Filename)%(Extension)" />`，让资源名与相对路径一一对应；或改用 `WithCulture`/自定义 `LogicalName`。
2. 若坚持靠名字推断，至少在解压后**校验每个资源确实落到了预期路径**，或对"主干含点"的资源**显式抛异常**，把静默白屏变成启动期失败。
3. 在 README 的快速开始里补一句限制说明（如果是短期不改）。

**证据**：读码推演 + 对 demo `wwwroot` 实际文件名清单的核对（证明当前未被触发）。

### 4.5 【中】自启配置文本的参数引号转义不完整（Windows 反斜杠结尾 / freedesktop 规范字符）

**位置**：`src/OrielWeb/Integration/OrielAutoStart.cs:96-99`

```csharp
private static string QuoteArgument(string argument)
    => argument.Length == 0 || argument.Contains(' ') || argument.Contains('"')
        ? "\"" + argument.Replace("\"", "\\\"", StringComparison.Ordinal) + "\""
        : argument;
```

**两个独立缺陷**：

**(a) Windows：参数以 `\` 结尾时引号失衡。** `CommandLineToArgvW` 的规则是"引号前连续反斜杠数为奇数时，`\"` 表示字面引号"。于是

```
--path=C:\dir\   →   "--path=C:\dir\"   →   解析结果：--path=C:\dir"（引号未闭合，后续参数被吞）
```

**正确做法**是先把参数尾部的反斜杠加倍，再整体加引号。

**(b) Linux：未按 freedesktop 规范转义。** Desktop Entry 规范要求：参数加双引号时，`"`、`` ` ``、`$`、`\` **四个字符都必须用反斜杠转义**。当前只转义了 `"`。例如参数 `--path=C:\temp` 会写出 `"--path=C:\temp"`，遵循规范的解析器（如 GLib 的 `g_shell_parse_argv`）会把 `\t` 当转义序列，得到 `--path=C:temp`。

**影响**：仅影响**含空格或引号**的参数（`QuoteArgument` 的触发条件），且参数来自应用自身而非页面，所以严重度是中低。但 ROADMAP 特意把"自启项写错不会当场失败，等用户下次开机才发现"当作要防的事，这里正是同一个失效模式的另一面——而且现有 13 个单测覆盖的都是"含空格"这类正例，**没有覆盖"含反斜杠/特殊字符"的反例**。

**建议**：
- Windows 侧改用"尾部反斜杠加倍"的完整规则（或直接调用标准的引号算法）。
- Linux 侧按规范补齐 `` ` ``、`$`、`\` 的转义。
- 两个平台各补 2–3 个反例单测（`--path=C:\a\`、`--path=C:\temp`、`--x=$HOME`、``--x=`cmd` ``）。

**证据**：读码 + `CommandLineToArgvW` / freedesktop Desktop Entry 规范语义推演。

### 4.7 【中低】单实例的锁文件与管道名放在共享临时目录，多用户环境下可被抢占

### 4.8 【中低】IPC 的 `id` 若非整数，回执 id 会退化为 0，导致页面 Promise 挂到 30 秒超时

**位置**：`src/OrielWeb/Ipc/OrielCommandDispatcher.cs:44-46`（取值）与 `:71-74`（兜底）

```csharp
int id = message.TryGetProperty("id", out var idElement) && idElement.ValueKind == JsonValueKind.Number
    ? idElement.GetInt32()      // ← 1.5 / 1e30 / 999999999999 会抛 FormatException
    : 0;
```

抛出的异常确实被调用方的 `try/catch` 兜住了（`Win32WindowHost.DispatchInvokeAsync`、`LinuxWebMessageHandler.DispatchInvokeAsync`），**不会崩**——但兜底回执写死了 `"id":0`：

```csharp
PostMessageOnUi($"{{\"__oriel\":\"result\",\"id\":0,\"ok\":false,\"error\":{…}}}");
```

而页面侧 `_onResult(id, …)` 只在 `pending` 里找得到对应条目才 settle。页面的 `seq` 从 1 开始，**`id:0` 永远匹配不到**。于是：页面发出一条 `id` 为浮点的 invoke（自己写前端时的笔误），得到的是**沉默 30 秒直到超时**，而不是立刻报错。

**建议**：`id` 解析失败时不要抛——`TryGetInt32()` 失败就取 0 并**在回执里回传原始 id 或显式拒绝**；更简单的是把 `id` 的解析也包进 `try`，并在兜底路径里尽量回传页面给的原值。至少应让页面的 Promise **立即 reject**，而不是等 30 秒。

**证据**：读码 + 桥接 JS 的 `pending` 匹配逻辑推演。

### 4.12 【低】其他观察（不构成缺陷，但值得记一笔）

- **`EmbeddedAssetExtractor` 每次启动全量重写资源，且不清理已删除的资源**。前者是启动期 I/O 与磁盘写入的浪费（无版本戳可跳过）；后者更值得注意——**从新版本里删掉的前端文件会残留在解压目录里继续被服务**，页面上"删掉的旧资源"仍然可访问。

### 5.1 Native AOT 发布：本环境跑不通，**原因是安全策略拦了 `reg.exe`，不是项目**

> **2026-10-01 更正。** 本节最初写的是"Windows SDK 的库文件未安装完整"，**那是错的**。
> 库文件一直都在。真实原因见下面的定位过程。AOT 发布在本机是**可用**的。

原始报错（强制走一遍全新原生编译后稳定复现）：

```
Generating native code
LINK : fatal error LNK1181: 无法打开输入文件"advapi32.lib"
→ Microsoft.NETCore.Native.targets(396,5): error MSB3073: link.exe 退出，代码 1181
```

**定位过程，以及最初为什么判错：**

1. 最初用 `find "/c/Program Files (x86)/Windows Kits" -name "advapi32.lib"` 搜不到，
   就下了"SDK 库缺失"的结论。**`find -name` 是大小写敏感的**，而实际文件名是
   `Windows Kits/10/Lib/10.0.26100.0/um/x64/AdvAPI32.Lib`——大写 `API` 让它被漏掉了。
   一次典型的"用错工具就下结论"。
2. 把原生编译产物目录挪开、强制重新编译后，失败稳定复现，而且同一条命令的 stderr 每次都出现：
   `PROGRAM BLOCKED BY SECURITY POLICY … reg.exe`。
3. 即使关闭沙箱重跑，`reg.exe` 仍被拦——该拦截属于**独立的程序黑名单策略**，
   无法从命令内绕过（提示要求用户到"安全中心 → 命令安全 → 程序黑名单"里移除）。

**结论**：ILCompiler 的原生链接步骤要靠 `reg.exe` 探测 Windows SDK；被拦之后 `LIB` 里少了
SDK 的 `um\x64`，链接器自然找不到 `AdvAPI32.Lib`。**这是本机策略限制，与项目无关**，
也正好解释了为什么用户自己的 `publish.ps1` 能正常出包。

**对 README 声明的复现程度**：评审者仍**无法独立跑通** AOT（`reg.exe` 拦不掉），
但有了用户侧产物的旁证，可以部分确认：

| README 声明 | 旁证 | 判定 |
|---|---|---|
| 发布为**原生单文件** | `publish/win-x64/OrielDemo.exe` 是 5.58 MB 的正常 PE（`MZ` / `PE\0\0`） | ✅ 成立 |
| WebView2 加载器已内嵌、**无旁文件** | 产物目录里只有 `OrielDemo.exe` + `OrielDemo.pdb` + `OrielWeb.pdb` + `OrielWeb.xml`，没有任何 loader DLL | ✅ 成立 |
| `OrielDemo.exe` **4.81 MB**、PDB **21 MB** | 实测 **5.58 MB** / **25.40 MB** | ❌ **数字过时**（见 §4.10 表末行） |

## 6. 结论与建议的处置顺序

**总体判断**：代码质量与工程纪律都在高水位，**没有发现阻断级缺陷**。问题集中在"静默失败模式"与"文档漂移"两类——这恰好是最难被单测发现、也最容易被"全绿"掩盖的两类。

**建议的处置顺序**：

| 顺序 | 事项 | 对应 |
|---|---|---|
| 1 | 修单实例锁的异常判定（静默不启动） | §4.1 |

| 3 | 修正 README/ROADMAP 关于 Windows 通知的三处描述（含"验证账"的失实断言） | §4.2 |
| 4 | 修内嵌资源解压器的点号路径映射（或至少在 README 写明限制并把静默白屏改成显式失败） | §4.3 |

**给发布的一句话建议**：第 1–3 项修完即可对外发 `v0.1.2`；第 4 项建议一并修，因为它面向的是"照着 README 上手的新用户"，正是最容易被静默白屏劝退的人群。

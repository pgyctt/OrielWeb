# OrielWeb 全面健康度评审报告

- **评审日期**：2026-10-05
- **评审对象**：`main` 分支 `311d6f1`（tag `v0.3.0`），工作区干净
- **评审范围**：架构与模块设计、代码质量 + 测试、文档与一致性、健壮性 + 构建发布（全维度）
- **评审方式**：热点逐行深读（IPC/能力门禁、oriel:// 资产链路、三平台 WindowHost、源生成器/打包/CI）+ 其余抽查 + 实测验证（构建 + 全套测试）；全部 P1 发现在入报告前已对照源码逐条复核
- **基调**：标准平衡；P0=安全/正确性缺陷必须修，P1=高风险或重要缺口，P2=应改进，P3=建议/风格

---

## 1. 总体结论

**这是一个工程纪律明显高于平均水准的库，安全核心设计正确、无 P0 级缺陷，可以继续按当前路线演进；需要处理的是 5 个 P1——全部是"承诺与实现脱节"或"默认/边缘路径未覆盖"类问题，而非方向性缺陷。**

一句话健康度判定：**安全模型与三平台一致性有结构性保证（不是靠巧合），文档与代码同步度经 20 项抽查零漂移，实测 413 + 74 用例全绿零警告；主要债务集中在生命周期收尾（销毁/挂起/泄漏）、Windows 默认（非无边框）路径的失修，以及少数"文档承诺了但代码没做"的落差。**

问题统计：**P0 × 0，P1 × 5，P2 × 19，P3 × 25+**（P3 以表格汇总）。

## 2. 亮点

1. **安全门禁是"结构性成立"而非"检查项齐全"**。来源 + 令牌校验先于命令名解析（`src/OrielWeb/Ipc/OrielCommandDispatcher.cs:68-74`，被拒消息连命令名都不读）；不可信页面在注入期就不装桥、`window.oriel` 根本不存在（`src/OrielWeb/Bridge/oriel-bridge.js:26-36`），宿主侧再判一次只是纵深；令牌用 CSPRNG 128 位 + `CryptographicOperations.FixedTimeEquals` 恒时比较（`src/OrielWeb/Ipc/OrielIpcToken.cs:22-46`）；Release fail-closed 的取值方向正确，元数据与 JIT 探测双路都取不到时按 Release 处理（`src/OrielWeb/Ipc/OrielBuildConfiguration.cs:52-53,77-98`）。
2. **零反射是真实的**。路由由增量源生成器编译期生成 switch 分发（`src/OrielWeb.Generators/OrielCommandGenerator.cs:20-30`，`ForAttributeWithMetadataName` + record 中间模型），经生成代码内 `[ModuleInitializer]` 注册、分发器构造期一次快照，热路径 O(1) 无锁无分配（`OrielCommandDispatcher.cs:44,123`）；CI 的三平台 AOT 发布 + 产物自检是实证。
3. **三平台一致性靠结构保证**。oriel:// 三平台复用同一 `AssetUrl.TryResolve` + `EmbeddedAssetStore.TryGet`（`Win32AssetScheme.cs:124` / `LinuxAssetScheme.cs:96` / `MacOSObjCClasses.cs:663`），平台代码只写"应答层"；桥接 JS 是单一模板 + 8 个占位符（`src/OrielWeb/Ipc/OrielBridgeTemplate.cs:40-57`），"三份手抄脚本缺陷同步传播"的根因被消灭。基线一致性是 CI 三平台真跑探针量出来的，不是推断。
4. **穿越防护是"决定"而非"巧合"**。`NormalizeRequestPath` 显式拒绝 `..`/`.` 段，输出是字典键而非文件系统路径，查表 miss 即 404（`src/OrielWeb/Assets/EmbeddedAssetStore.cs:135-152`）；`..%2F`、`%5c` 变体有测试钉住（`tests/OrielWeb.Tests/AssetUrlTests.cs:49-65`）。
5. **构建期左移做得完整**。旧式 EmbeddedResource 写法触发构建错误 ORIELWEB001（`src/OrielWeb/buildTransitive/OrielWeb.targets:119-127`）+ 运行期兜底报错并指路（`EmbeddedAssetStore.cs:196-206`）+ `tools/verify-pack.ps1` 四场景机器断言 + 回归测试，四层防线。
6. **CI 是"真取证"**。三平台都跑 AOT 产物自检并以日志结论行判定（退出码不可靠的教训写进了注释，`.github/workflows/ci.yml:178-197,332-409,411-447`）；失败写 GitHub 注解；甚至有"macOS bash 中文变量名"事故守卫（`ci.yml:126-149`）。
7. **踩坑知识沉淀为代码旁注释**。`GtkNative.cs:240-251`（返回值 marshal 成 string 会写坏栈）、`Win32Native.cs:659-664`（RegSetValueEx 参数误用史）、`MacOSObjCClasses.cs:604-627`（协议必须显式声明）、`LinuxSignalHandlers.cs:149-154`（GTK maximize 状态须 idle 后读）——这是二次评审最有价值的资产。
8. **文档与代码同步度罕见地高**。docs/API.md 抽查 20 个公共 API 签名 20/20 一致；ROADMAP 的三项已知缺口（Range 请求、window.open、升级残留目录）逐条到源码核实为真，"明确不做"清单诚实。
9. **实测全绿**：构建 0 警告 0 错误（`TreatWarningsAsErrors` 覆盖 src/），413 个 xunit 用例 + 74 个桥接 JS 用例全部通过；TODO/FIXME 几乎为零。
10. **不对称处全部显式记录而非假装支持**：`ShowFolderDialog` 丢弃 initialDirectory、macOS 通知忽略 appId、Linux `ToggleMaximize` 返回意图值——取舍都有书面理由。

## 3. 问题清单

### 3.1 P1（高风险/重要缺口，共 5 项，全部已复核原文）

**P1-1【IPC/安全】异常消息未按文档承诺净化，原文直达页面**
- `docs/API.md:291` 明确承诺"抛别的异常则给通用失败文本"，但 `src/OrielWeb/Ipc/OrielCommandDispatcher.cs:116-119,135-138` 对**所有**异常 `ReplyError(ex.Message)`；三平台兜底 catch 同样回 `ex.Message`（`Win32WindowHost.cs:999-1003`、`LinuxWebMessageHandler.cs:94-97`、`MacOSWebMessageHandler.cs:94-97`）。
- 非受控异常（`IOException` 等）的 Message 常含内部路径/主机名/端点，是 XSS 场景下的探测放大器；更严重的是开发者会**相信文档已有的净化而不设防**。
- 建议：分发器只对 `OrielIpcException` 透传 Message，其余回通用文案、细节走 `Debug.WriteLine`，并补单测钉住（透传/通用文案/不含堆栈三条钉子）。

**P1-2【Windows】默认 framed 窗口丢失系统边框渲染与边缘 resize**
- `src/OrielWeb/Platform/Windows/Win32WindowHost.cs:617-638` 的 `WM_NCCALCSIZE` 分支对**所有**窗口返回"客户区=窗口矩形"（注释写"无边框窗口"但代码无 `_options.Frameless` 判定，引入记录 `92fb313` 确系为无边框所加）；而 `WM_NCHITTEST` 的边缘命中只在 `_options.Frameless && _options.Resizable` 时接管（:645）。
- 组合效果：framed（库默认值）窗口非客户区被压成零 → 无标题栏边框，且 `DefWindowProc` 一律返回 HTCLIENT → **边缘无法拖拽调整大小**。Linux（`gtk_window_set_decorated`）与 macOS（`StyleTitled`）的 framed 模式均正常，Windows 独坏。示例与全部自检只用 `WithFrameless()`，默认路径零覆盖。
- 建议：确认设计意图。若 framed 模式受支持：`HitTestResizeBorder` 的条件放宽为 `_options.Resizable`（或 framed 时不动 `WM_NCCALCSIZE`），并把 framed 窗口的标题栏可见性与边缘 resize 加进 ManualCheck 清单；`ComputeStyle`（:424-444）可抽单测防回归。

**P1-3【Linux/macOS】`ExecuteScriptAsync` 的 pending eval 永不清理，公开 API 可永久挂起**
- `src/OrielWeb/Platform/Linux/LinuxWebMessageHandler.cs:121` / `src/OrielWeb/Platform/MacOS/MacOSWebMessageHandler.cs:121` 只注册不清理；窗口销毁路径（`LinuxWindowHost.cs:574-588` / `MacOSWindowHost.cs:547-567`）不清 `_pendingEvals`；eval 依赖页面回环（`LinuxWindowHost.cs:958-974` / `MacOSWindowHost.cs:804-830`），页面在 eval 与回执之间导航/销毁时结果永不返回。
- 表现：公开 API `WebviewWindow.EvaluateJs` 永远 await，无超时、无取消。
- 建议：宿主销毁与 load-started 时逐个 `TrySetException` 清空 pending 表；可选加超时。回环协议（JS 包装串 + `"E:"` 错误前缀）可抽公共纯函数共享测试。

**P1-4【Linux】oriel:// `OnRequest` trampoline 顶层无异常保护，托管异常逃逸即进程崩溃**
- `src/OrielWeb/Platform/Linux/LinuxAssetScheme.cs:83-144`：资源读取有内层 try（:111-121），但 `Marshal.AllocHGlobal`（:123）、`Marshal.Copy`、`GMemoryInputStreamNewFromData`、`WebkitUriSchemeRequestFinish` 都在保护圈外。该函数经 `[UnmanagedCallersOnly]` 函数指针被 GLib 直接调用，托管异常逃逸的结果是运行时 fail-fast、整个进程终止——正是 macOS 侧注释"trampoline 必须全身 try/catch"（`MacOSObjCClasses.cs:643-727`）防的那个坑，Linux 侧没做到。
- 建议：整个 `OnRequest` 包一层 try/catch，兜底走 `FinishWithError`。改动约几行，收益/成本比全场最高。

**P1-5【打包/运行】类库 wwwroot 的传递性承诺在运行期落空（静默 404）**
- `src/OrielWeb/OrielWeb.csproj:32-33` 注释宣称 buildTransitive 使"应用 → 引用一个带 wwwroot 的类库 → 那个类库的资源也会被正确嵌入"；targets 确实把类库 wwwroot 嵌进**类库程序集**，但运行期 `EmbeddedAssetStore.Create` 只扫 `Assembly.GetEntryAssembly()` 的资源（`src/OrielWeb/Assets/EmbeddedAssetStore.cs:57-61`，全仓库仅此一处扫描）。
- 类库的前端资源永远不被服务，表现为静默 404——恰是本仓库最痛恨的失败形态。
- 建议：二选一——运行期扫描入口程序集 + 引用程序集（AOT 下注意裁剪），或删改 csproj 注释并明示"类库 wwwroot 目前不受支持"。

## 4. 分维度详评

### 4.1 架构与模块设计

分层清晰：`App/`（装配与 builder）→ `Ipc/`（门禁与分发）→ `Bridge/`（注入模板）→ `Platform/{Windows,Linux,MacOS}`（应答层）→ `Generators`（编译期路由）。三平台一致性不是靠约定而是靠结构：解析、MIME、桥接脚本、路由生成都是单一来源，平台代码只写差异层。能力门禁的纯函数化（`OrielCapabilityMatch/Rules` 全 Ordinal、无文化规则后门）使安全判据可逐例钉测。设计取舍基本都有书面理由（代码注释 + API.md "为什么"章节）。

需要面对的架构级决策有三处：① async 命令的线程模型平台不对称（P2-3）；② oriel:// 的"同步全量应答"模式换来的简洁性以大文件内存与媒体不可用为代价（P2-6 + 已声明 Range 缺口）；③ 进程级全局状态（命令注册表、Linux scheme 单例、`s_current`）对"单进程单应用"成立，多应用同进程场景的边界尚未显式划定。

### 4.2 代码质量与测试

代码卫生极好：TODO 几乎为零、警告零容忍、原生资源 try/finally 纪律、`[UnmanagedCallersOnly]` 全身 try/catch、P/Invoke 签名经逐条核对（1 处 GTK3 签名错误，P3 级）。测试 250 个特性展开 413 例 + 桥接 74 例，纯逻辑层覆盖扎实（能力门禁 27、对话框 26、分发器 22……）。

缺口集中在两处：**三平台 WindowHost（约 4000 行）零单测**——但这不是不可救：`LinuxResizeSupport` 等已有"抽纯函数 + 测试"的先例，坐标换算/样式计算/托盘解析/eval 回环协议等十余处可照此模式抽出（见第 5 节清单）；**组合路径零覆盖**——门禁在 `CapabilityTests` 里直接调用，但没有用例走 `HandleInvokeAsync` 端到端验证"坏令牌/坏来源 → 回执 ok:false + id 回写"，安全模型与分发器之间的接缝恰是最容易在重构中断裂的地方。此外自检八项全部基于 Frameless 窗口，P1-2 这类默认路径问题只有代码审读能发现。

### 4.3 文档与一致性

文档同步度是本仓库最强的资产之一：20 个 API 签名抽查零漂移；README 的平台矩阵、命令、路径与现状一致；ROADMAP 的三项已知缺口（Range、window.open、升级残留）逐条到源码核实为真——"已知缺口"被诚实文档化，而不是隐藏。API.md 的"每章为什么"写法把取舍变成了资产。

不一致点均属措辞级：令牌"每进程" vs "每应用实例"（P3）、异常净化承诺未兑现（P1-1，唯一的"承诺了但没做"）、framed 窗口与 `At()` 的平台差异未标注（P1-2/P2-10）。仓库卫生方面：根 agents.md 为通用提问协议（建议另立工程规范文件）、无 CHANGELOG、0.1.3–0.1.7 版本无 tag（P2-18）、磁盘死目录未跟踪但易困惑后来者。

### 4.4 健壮性与构建发布

构建链路质量高：`TreatWarningsAsErrors` + 全套 AOT/Trim 分析器、ORIELWEB001 四层防线、发布脚本防御性强（RID 校验、"产物目录是仓库祖先则拒删"守卫、WSL 脚本的引号地狱规避）、release.yml 有 tag↔版本一致性闸。CI 是三平台真取证而非弱断言。

健壮性短板集中在**生命周期收尾**：销毁路径不清 pending eval（P1-3）、不清上下文菜单（P2-8）、Linux `_gtkWindow` 不清零（P2-14）、Create 中段异常泄漏（P2-7）、macOS 每请求泄漏 response 对象（P2-5）。这些全是" happy path 完好、收尾路径失修"的同一类病，适合一次性专项清理。发布流程的两个洞（dispatch 旁路版本闸、macOS 打包路径矛盾）都是配置级小改。

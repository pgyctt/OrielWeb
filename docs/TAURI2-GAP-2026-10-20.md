# OrielWeb vs Tauri 2 差异基线（2026-10-20，0.4.0 之后）

> 参照实现：`@tauri-apps/api` **2.12.4**、官方插件 `plugin-*` 2.x（`packages/api/package.json` 的 devDependencies）。
> 取证方式：`node --test packages/api/tests/tauri-alignment.test.mjs`（8 条全绿）+ 逐模块导出/方法枚举 + 官方插件页清点。
> 这份文档是**新基线**，不替代 10-18 的[审计](TAURI2-ALIGNMENT-AUDIT-2026-10-18.md)与[执行计划](TAURI2-ALIGNMENT-EXECUTION-PLAN-2026-10-18.md)——那两份记录"怎么补"，这份记录"补到哪了、还剩什么"。

## 0. 一句话结论

**页面 API 面已经接近可用，剩下的是"生态"与"工程链路"，不是"还差几个函数"。**

- Tauri 核心 API **12 个模块，本库有 10 个**（缺 `tray`、`webview`）。
- 16 个已对齐模块的导出符号：**参照 167，本库 126，差 52 个**（其中 25 个是本库扩展），
  缺口高度集中在 4 个模块：`notification` 16、`fs` 10、`app` 8、`core` 7。
- `Window` 类方法 **84 → 60**，缺 26 个：23 个是方针明确不做（跨平台不一致），2 个可做未做，1 个内部方法。
- 官方插件 **32 个，本库对齐 6 个**；缺的 20 个桌面相关插件里，`updater` / `window-state` / `global-shortcut` / `store` 是真实应用最常撞的。
- 框架层差异是整块的：**没有配置文件、没有 CLI、没有插件机制、没有移动端、没有自动更新、没有 ACL 权限文件、没有 CSP/隔离模式**。

按迁移成本排序，真正的门槛不在 API 名字上：

```
① 插件生态（整块能力，无法用"加个命令"等价）
② 检测不到但不报错的语义差异（__TAURI_INTERNALS__、命令名、线格式）
③ 工程链路（CLI / 配置 / 权限文件 / 打包与更新）
④ 页面 API 的剩余符号（大多是移动端或边缘能力）
```

### 1.3 这条账本本身够不够

够用，但有三处盲点，都不影响当前测试的绿：

1. **`PLANNED_MODULES` 的 `batch` 指向已完成的批次**。`tray` 写着 `B6b`、`webview` 写着 `B4`，
   而 B4/B6b 在进度表里都是 ✅。断言只校验 `/^B\d/`，不校验"批次是否已完成"——
   于是"批次做完了、模块还没建"这种状态没有任何东西盯着，账本会安静地过期。
2. **覆盖边界是 16 个模块**。插件生态（20 个桌面插件）、框架层（CLI/配置/权限/更新/移动端）
   完全在账本之外。它们不会出现在任何一条断言的失败信息里。
3. **统计口径是"符号个数"**，这正是 `MIGRATION-FINDINGS.md` §6 已经指出过的误导：
   `Channel` 与 `onBackButtonPress` 在账本上都是"缺 1"，成本差十倍。**缺口数不等于工作量。**

## 2. 第二层：插件生态（最大的一块）

Tauri 2 官方插件 32 个（含 `system-tray`、`window-customization` 两个新条目）。本库对齐情况：

| 状态 | 插件 |
|---|---|
| ✅ 已对齐（6） | `autostart`、`clipboard-manager`、`dialog`、`fs`、`notification`、`opener` |
| ⚠️ 能力有、模块无（2） | 托盘（`api/tray`）、菜单（已在 `api/menu`，Tauri 另有 `window-customization`） |
| ❌ 缺（桌面相关 20） | `cli`、`deep-link`、`global-shortcut`、`http`、`localhost`、`log`、`os`、`persisted-scope`、`positioner`、`process`、`shell`、`single-instance`、`sql`、`store`、`stronghold`、`updater`、`upload`、`websocket`、`window-state`、`window-customization` |
| ➖ 不适用（移动端 8） | `barcode-scanner`、`biometric`、`geolocation`、`haptics`、`nfc`、`torch`、`upload`（部分）、`deep-link`（部分） |

**为什么这块补不上"顺手"**：Tauri 插件是 `Rust crate + JS 包 + 权限清单` 三件套，
本库没有插件机制，替代路径只有「在 `[OrielCommand]` 里自己写一遍」。这不是对齐，是重写。

按真实应用的撞击频率（证据见 `MIGRATION-FINDINGS.md` §3）：

| 插件 | 影响面 | 迁移时的现实做法 | 补齐成本 |
|---|---|---|---|
| `updater` | 有更新功能的应用必撞 | 接 Velopack 的应用侧（`VelopackApp.Build().Run()`），或删掉更新入口 | **高**（但 Velopack 已把打包做了一半） |
| `window-state` | 几乎所有桌面应用都该有 | 自己 store 尺寸/位置，启动时 `WithSize`/`WithPosition` | 中（库内做一次即可，收益高） |
| `global-shortcut` | 工具类应用高频 | 平台各自注册（Win32 `RegisterHotKey` / GTK / Carbon） | 中高，三套原生 |
| `store` | 高频 | 自己写 JSON 文件（`fs` 已够用） | 低（但每应用各写一遍） |
| `os` | 中频 | `Environment.OSVersion` 自己给 | 低 |
| `process.relaunch` | 中频 | `exit` 后由外部拉起，或 `Process.Start` 自己 | 低中 |
| `log` | 中频 | 自己接日志库 | 低 |
| `http` / `websocket` / `sql` / `stronghold` | 低频（可用浏览器 API / 自带库替代） | 前端 `fetch`/`WebSocket`；数据库用 .NET 库 | 不做 |

> **一个容易被忽略的对照**：`http`/`websocket` 在 Tauri 里存在的理由是"绕过 CORS、
> 用 Rust 侧证书与代理"。本库里页面是 `oriel://` 安全来源，`fetch` 受 CORS 约束，
> 跨域请求要么配服务端 CORS、要么走自定义命令。这是**能力差异**，不是缺一个函数。

## 3. 第三层：框架与工程链路（账本完全看不见）

| 维度 | Tauri 2 | OrielWeb 现状 | 差异性质 |
|---|---|---|---|
| 项目配置 | `tauri.conf.json`（窗口/打包/安全/插件全在里面） | **没有配置文件**，全部代码 API（`Oriel.CreateBuilder()`） | 设计选择；好处是无 schema 漂移，坏处是没有"声明式"入口与工具链生态 |
| 权限模型 | `capabilities/*.json` + ACL（`permissions/`、scope、运行时 `checkPermissions`） | `UseCapabilities(c => c.Allow(...))` 代码配置，构建期 fail-closed | 形态不同；缺运行时查询与 scope 持久化（`persisted-scope`） |
| CLI | `tauri dev` / `tauri build` / `tauri icon` / `tauri android` | 无 CLI，`dotnet build/publish` + `tools/*.ps1` | 缺"一条命令跑起开发态"的体验（`tauri dev` 含 dev server 联动与热重载） |
| 插件机制 | Rust crate + JS 包 + 权限清单，可发布第三方插件 | **无**。扩展点只有 `[OrielCommand]` 自定义命令 | 结构性差异：本库是库不是平台 |
| 移动端 | Android / iOS 一等公民 | **明确不做** | 定位差异 |
| 自动更新 | `plugin-updater` + 签名清单 + 静态托管 | 打包交给 Velopack，**应用侧更新未接** | 缺口，成本高但路径已定 |
| 安装包 | 自带 bundler（msi/dmg/deb/AppImage/NSIS） | Velopack（Setup.exe/msi/AppImage/pkg） | 已等价，签名与公证未做 |
| CSP | `app.security.csp` 注入 | **无**（不注入 CSP header） | 安全面缺口 |
| 隔离模式 | Isolation Pattern（注入隔离脚本，防前端被篡改后直连 IPC） | **无** | 安全面缺口 |
| 多 webview | 一个窗口挂多个 webview，可 `reparent` | 窗口即 webview | 结构性不做 |
| 窗口状态持久化 | `plugin-window-state` | 无 | 缺口，易补 |
| 单实例 | `plugin-single-instance`（带 argv 回传给首实例） | `SingleInstanceGuard`（唤醒首实例，**argv 不回传**） | 半对齐 |
| 托盘 | `api/tray`（`TrayIcon` 类）+ 可选 `system-tray` 插件 | C# `OrielTray` + 桥接 `oriel.tray`，**npm 模块缺** | 半对齐 |
| 菜单 | `api/menu` + `window-customization` | `api/menu` 已对齐（popup + app/window menubar） | 基本对齐 |
| 开发态体验 | `tauri dev` + HMR + devtools | `UseDebug()` 开 DevTools；dev server 要自己起并 `AllowOrigin` | 体验差异 |

## 4. 第四层：语义差异（编译器看不见，最危险）

这一层不是"缺什么"，而是"看起来一样、行为不同"。B7 演练的结论是：**这几条比所有缺能力项加起来更影响迁移是否成功**。

| # | 差异 | 症状 | 现状 |
|---|---|---|---|
| 1 | 没有 `window.__TAURI_INTERNALS__` | 应用静默走进浏览器降级分支（假数据、禁用按钮、不注册监听） | 提供 `isTauri()`；无兼容标记（有意） |
| 2 | 命令名不同（`plugin:fs\|read_text_file` → `fs.readTextFile`） | `invoke()` 抛"未知命令"；测试桩按旧线格式写会全红 | 映射表在 `MIGRATION-FINDINGS.md` §4 |
| 3 | 事件名不同（`tauri://` → 本库的宿主事件名） | 监听不触发 | `toHostEventName()` 兜住；`TauriEvent` 常量已逐键对齐 |
| 4 | 序列化线格式：本库 `{ type: "Logical", x, y }`（Tauri 1 形状），Tauri 2 是 `{ Logical: { x, y } }` | 页面看不出差别，宿主只认前者 | **有意分歧**（`METHOD_DIVERGENCES.__TAURI_TO_IPC_KEY__`） |
| 5 | `Channel` 不保证重排（无 index） | 高并发流式推送可能乱序 | 有意取舍，已写进 API.md §11.3 |
| 6 | `menu.close()` 同名不同义（关在屏菜单 vs 释放 rid） | 不抛错，也不释放资源（本来就没有） | 有意分歧 |
| 7 | `menu.popup()` 在 Windows/macOS **阻塞**、Linux 异步 | `await popup()` 之后用户已选完 | 已实测取证并写进文档 |
| 8 | `Image.close()` 不存在 | `await image.close()` 抛 `TypeError` | 有意（无资源可释放，宁可当场炸） |
| 9 | 内嵌资源是 `oriel://<host>`，不是 `tauri://localhost` / `asset://` | 依赖 `location.origin` 的前端代码行为不同 | 有意；`convertFileSrc` 固定走 `oriel://file.oriel/` |
| 10 | `fs` 无句柄、`dialog` 返回形状、`path` 无 `BaseDirectory` | 部分调用点必须改写 | 已登记在 GAPS |

## 5. 从"能不能迁"看，还剩多少

| 应用类型 | 结论 |
|---|---|
| 单窗口工具（dialog + fs + clipboard + opener + 自定义命令） | **可迁**。B7 演练的 random-frame 属于这类，机械改写 import 即可，剩下 3 处能力缺口 |
| 多窗口 / 停靠面板 | **可迁**。`window.new` + `webviewWindow` 已补；缺 `webview` 层（面板内嵌套 webview 的应用要改架构） |
| 托盘 / 菜单密集型 | **可迁**。能力齐全，但 npm 模块缺一个 `tray`，前端调用点要改成 `oriel.tray` |
| 依赖 `plugin-updater` / `window-state` / `global-shortcut` | **需额外工作**。前两个建议库内补（收益高、成本中），第三个按需自建 |
| 依赖 `store` / `sql` / `stronghold` / `http` | **不改架构就迁不了**，要么换实现，要么自己写命令 |
| 移动端应用 | **不适用**，定位不同 |

## 6. 建议的下一批（按"真实撞击 × 成本"排）

> **本节已由 2026-10-20 的逐项决策取代**——见
> [TAURI2-ALIGNMENT-DECISIONS-2026-10-20.md](TAURI2-ALIGNMENT-DECISIONS-2026-10-20.md)：
> 决策基调是**全量对齐**（含补壳与线格式改造），新批次为 B12–B24。下面保留原建议作对照。

1. **`@orielweb/api/tray`（B12）**——能力全在，只缺一个包的形状（`TrayIcon` 类 + `new/getById/removeById`）。
   半天量级，直接把"托盘"从"半对齐"变成"对齐"。
2. **`window-state`（B13）**——三平台都不用写原生代码，存尺寸/位置/最大化状态即可。
   几乎所有桌面应用都需要，属于"库内做一次、所有应用受益"。
3. **`plugin-os` + `plugin-process.relaunch`（B14）**——薄，`Environment` + `Process.Start` 就够。
4. **`fs` 句柄式 API（B15）**——`open/create/FileHandle/watch`。大文件与日志场景的真实需求，
   但三平台各自的文件监视机制不同（`ReadDirectoryChangesW` / `inotify` / `FSEvents`），成本中高。
5. **Velopack 应用侧更新（B16）**——`Main` 首行 `VelopackApp.Build().Run()` + `UpdateManager` 封装。
   打包已通，只差这一步。
6. **账本补两条断言**（半小时）：`PLANNED_MODULES` 的 `batch` 不得指向已完成的批次；
   新增一个"插件生态覆盖清单"，让 20 个缺失插件也进入可断言的账，而不是散在文档里。

不建议现在做：`webview` 模块（结构性不做）、`http`/`websocket`/`sql`/`stronghold`（生态级，且可用现成方案替代）、
移动端（定位不同）、`setEffects`/任务栏进度一类 A 组窗口能力（三平台语义不一致，做出来是三套不同的东西）。

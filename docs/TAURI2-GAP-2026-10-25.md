# OrielWeb vs Tauri 2 差异基线（2026-10-25，0.5.0）

> 参照实现：`@tauri-apps/api` **2.12.4**（与 npm 上的 `latest` 一致，无版本脱节）、官方插件按
> [tauri.app/plugin](https://tauri.app/plugin/) 支持表清点 **33 个**。
> 取证方式：`node --test packages/api/tests/tauri-alignment.test.mjs`（10 条全绿）、直接枚举
> `node_modules` 里的导出面、`grep` 实现核对框架层能力。**数字都是跑出来的，不是从文档抄的。**
>
> 这是 10-20 [差异基线](TAURI2-GAP-2026-10-20.md)的**重新测量**，不是它的续写。那三份文档记录
> "怎么补"，这份记录"补到哪了、还剩什么、以及**哪里说错了**"。

## 0. 一句话结论

**页面 API 面已经基本清零，剩下的门槛全部在生态与工程链路上。**

- 17 个已登记模块：参照 **168** 个导出，本库 **165** 个（含 12 个有记录的扩展），**缺口 15**。
- 15 条缺口只来自三组原因：`core` 的插件运行时 7 条、`fs` 的 macOS 沙箱 2 条、
  `notification` 的 Android 通知模型 6 条。**没有一条是"忘了做"。**
- 方法层：37 个同名类比对，**0 缺口**；`Window` 的 26 项方法缺口在 B21/B22 后清零。
- 官方插件 33 个：对齐 6、形态等价 2、半对齐 1、**桌面相关缺失 18**、移动端不适用 6。
- 框架层整块差异仍在：**没有配置文件、没有 CLI、没有插件机制、没有 ACL 文件、没有 CSP、
  没有隔离模式、没有移动端、应用侧自动更新未接。**

所以"能不能迁"的答案分两半：**单窗口工具类应用可以零删改迁**（B24 演练里 24 个导入符号
的缺口从 3 降到 0）；**依赖 Tauri 插件生态或工程链路的应用迁不了**，因为缺的是机制，不是函数。

## 1. 相对 10-20 基线变了什么

| 指标 | 2026-10-20 | 2026-10-25 | 变化 |
|---|---|---|---|
| 已对齐模块 | 10 | **17** | +`tray`、+`webviewWindow` 等 |
| 导出缺口 | 52 | **15** | B12–B24 落地 |
| `Window` 类方法缺口 | 26 | **0** | B21 光标 6 + B22 平台开关/特效/任务栏 19 |
| 缺整个模块 | 2（`tray`、`webview`） | **1**（`webview`） | B12 补了 `tray` |
| 插件对齐 | 6 | **6** | 没变——B12–B24 全花在核心 API 上 |
| 线格式 | Tauri 1 形状 | **Tauri 2 形状** | B14，读兼容保留到 0.6.0 |
| npm 包 | 无 | **`@orielweb/api` 0.5.0** | 2026-10-24 首发 |

**一句话读法**：这一周补的全是"页面 API 的形状"，一块插件生态都没动。所以如果只做单窗口
工具，今天就能迁；如果用了 `plugin-updater` / `window-state` / `global-shortcut` / `store`，
该干的活与 10-20 一模一样。

### 2.2 剩余的 15 条，逐条为什么不做

| 组 | 条数 | 为什么不做 |
|---|---:|---|
| `core` 插件运行时 | 7 | `Resource` / `PluginListener` / `addPluginListener` / `transformCallback` / `SERIALIZE_TO_IPC_FN` / `checkPermissions` / `requestPermissions`。**这不是七个能力，是一个模型缺失的七个面**：本库没有"宿主侧对象表 + 插件注册协议 + 运行时权限查询"，造出来只能是假对象。 |
| `fs` macOS 沙箱 | 2 | `start/stopAccessingSecurityScopedResource` 需要 open 面板签发的 bookmark 与沙箱 entitlement。本库不做应用打包，给不出那个上下文。 |
| `notification` Android | 6 | `Importance` / `Visibility` / `channels` / `createChannel` / `removeChannel` / `registerActionTypes`。全是 Android 的 channel 与重要级、iOS 的动作类型；桌面上没有对应物。 |

### 2.3 方法层

37 个同名类比对，`METHOD_GAP_GROUPS` **空**——Tauri 的类方法我们一条不缺。剩下的是 10 条
**有意分歧**（每条都在账本里写了理由）：

| 分歧 | 性质 |
|---|---|
| `menu.close()` | **同名不同义**：Tauri 释放 `rid`；本库关掉在屏菜单（Windows 上 `popup()` 阻塞，没它页面无法用代码关菜单） |
| `menu.rid` | 本库没有资源表，菜单树是页面侧纯数据 |
| `Channel.cleanupCallback()` | 等价能力叫 `Channel.close()`，不给第二个名字 |
| `__TAURI_TO_IPC_KEY__` | 线格式已对齐，但序列化钩子仍走 `toJSON` |
| `_handleTauriEvent` | Tauri 内部方法 |
| `activityName` / `sceneIdentifier` | Android / iOS 专有 |
| `WebviewWindow.position` / `size` / `setAutoResize` / `reparent` | **结构性**：本库窗口即 webview，没有"窗口内偏移" |

### 2.4 唯一缺的模块：`webview`

不是"还没排到"，是**模型不存在**。Tauri 的 `Webview` 可以脱离窗口存在、可以在一个窗口里
挂多个、可以 `reparent`。本库一个窗口一个 webview、铺满客户区。B24 复核结论：继续不做。
真要用 `getCurrentWebview()` 的地方换成 `getCurrentWindow()` 即可（pier-dock 演练里唯一
的模块级缺口就是这么过的）。

## 3. 第二层：插件生态（最大的一块，且这一周毫无进展）

官方插件 33 个的当前状态：

| 状态 | 数量 | 插件 |
|---|---:|---|
| ✅ 已对齐 | 6 | `autostart`、`clipboard-manager`、`dialog`、`fs`、`notification`、`opener` |
| ⚙️ 形态等价 | 2 | `system-tray`（本库是 `api/tray` 而非插件）、`window-customization`（无边框 + 菜单栏已覆盖大部分） |
| ⚠️ 半对齐 | 1 | `single-instance`（有 `SingleInstanceGuard`，但**通知载荷不回传**——第二次启动带的文件路径传不进来） |
| ❌ 桌面相关缺失 | **18** | `cli`、`deep-link`、`global-shortcut`、`http`、`localhost`、`log`、`os`、`persisted-scope`、`positioner`、`process`、`shell`、`sql`、`store`、`stronghold`、`updater`、`upload`、`websocket`、`window-state` |
| ➖ 移动端不适用 | 6 | `barcode-scanner`、`biometric`、`geolocation`、`haptics`、`nfc`、`torch` |

按真实撞击频率（`MIGRATION-FINDINGS.md` §3 的取证）：

| 插件 | 影响面 | 迁移时的现实做法 | 补齐成本 |
|---|---|---|---|
| `updater` | 有更新入口的应用必撞 | Velopack 打包已通，**应用侧接入未做**（`VelopackApp.Build().Run()`） | 中（路径已定） |
| `window-state` | 几乎所有桌面应用都该有 | 自己存尺寸/位置，启动时 `WithSize`/`WithPosition` | **低**（库内做一次收益最高） |
| `store` | 高频 | 自己写 JSON（`fs` 已够） | 低，但每个应用各写一遍 |
| `global-shortcut` | 工具类高频 | Win32 `RegisterHotKey` / GTK / Carbon 各自写 | 中高，三套原生 |
| `process.relaunch` | 中频 | `exit` 后外部拉起，或 `Process.Start` | 低中 |
| `os` / `log` | 中频 | `Environment.OSVersion` / 自接日志库 | 低 |
| `http` / `websocket` / `sql` / `stronghold` | 低频 | 前端 `fetch`/`WebSocket`；数据库用 .NET 库 | 不做 |

> **`http`/`websocket` 不是"缺一个函数"**：它们在 Tauri 里存在的理由是绕过 CORS、用 Rust 侧
> 证书与代理。本库页面是 `oriel://` 安全来源，`fetch` 受 CORS 约束——跨域要么服务端配 CORS，
> 要么走自定义命令。这是**能力差异**。

> **为什么这块补不上"顺手"**：Tauri 插件是 `Rust crate + JS 包 + 权限清单` 三件套，本库没有
> 插件机制。替代路径只有"在 `[OrielCommand]` 里自己写一遍"——那不是对齐，是重写。

## 4. 第三层：框架与工程链路（账本完全看不见）

| 维度 | Tauri 2 | OrielWeb 0.5.0 | 差异性质 |
|---|---|---|---|
| 项目配置 | `tauri.conf.json`（窗口/打包/安全/插件） | **无配置文件**，全代码 `Oriel.CreateBuilder()` | 设计选择；无 schema 漂移，但没有声明式入口与工具链生态 |
| CLI | `tauri dev` / `build` / `icon` / `android` | 无 CLI，`dotnet build/publish` + `tools/*.ps1` | 缺"一条命令跑起开发态" |
| 权限模型 | `capabilities/*.json` + ACL（scope、`checkPermissions`、`persisted-scope`） | `UseCapabilities(c => c.Allow(...))`，构建期 fail-closed | 形态不同；**且是全局的**，没有按窗口/按远程 URL 细分；无运行时查询、无 scope 持久化 |
| 插件机制 | Rust crate + JS 包 + 权限清单，可发第三方插件 | **无**。扩展点只有 `[OrielCommand]` | 结构性：本库是**库**不是平台 |
| 移动端 | Android / iOS 一等公民 | **明确不做** | 定位差异 |
| 自动更新 | `plugin-updater` + 签名清单 + 静态托管 | Velopack **打包**已通，**应用侧更新未接** | 真实缺口，路径已定 |
| CSP | `app.security.csp` 注入响应头 | **无**（不注入 CSP） | 安全面缺口 |
| 隔离模式 | Isolation Pattern（防前端被篡改后直连 IPC） | **无** | 安全面缺口 |
| 多 webview | 一窗口多 webview，可 `reparent` | 窗口即 webview | 结构性不做 |
| 开发态体验 | `tauri dev` + HMR + devtools | `UseDebug()` 开 DevTools；dev server 自己起 + `AllowOrigin` | 体验差异 |

安装包这一格已经**等价**：Tauri 自带 bundler（msi/dmg/deb/AppImage/NSIS），本库交给
Velopack（Setup.exe/msi/AppImage/pkg），三平台都跑过。差的只是签名与公证。

## 5. 第四层：语义差异（编译器看不见，最危险）

这一层不是"缺什么"，而是"看起来一样、行为不同"。B7 演练的结论是：**这几条比所有缺能力项
加起来更影响迁移是否成功**。

下表 10 条里，2 条已在本次核对中处理掉（#2 修正实现、#7 更正归类），**实际仍需注意 8 条**。

| # | 差异 | 症状 | 现状 |
|---|---|---|---|
| 1 | 没有 `window.__TAURI_INTERNALS__` | 应用**静默**走进浏览器降级分支（假数据、禁用按钮、不注册监听）。3/3 演练应用都这么探测 | 提供 `isTauri()`；不提供兼容标记（有意）。**探测只能靠静态检查捕获**，见 §5.1 |
| 2 | ~~关闭接管的默认相反~~ | ~~页面什么都不做窗口就不关~~ | **已修正（2026-10-25）**：改成 Tauri 同一段逻辑——handler 跑完未 `preventDefault()` 即 `destroy()` |
| 3 | 命令名不同（`plugin:fs\|read_text_file` → `fs.readTextFile`） | `invoke()` 抛"未知命令"；测试桩按旧线格式写会全红 | 映射表在 `MIGRATION-FINDINGS.md` §4 |
| 4 | 事件名不同（`tauri://` → 宿主事件名） | 监听不触发 | `toHostEventName()` 兜住；`TauriEvent` 常量已逐键对齐 |
| 5 | `listen()` 返回**函数**（thenable），不是 `Promise` | `instanceof Promise === false`；`await listen(...)` 等三种写法都成立 | 有意（让同步取 unlisten 与异步两种写法共存） |
| 6 | `menu.close()` 同名不同义 | 不抛错，也不释放资源（本来就没有） | 有意分歧 |
| 7 | ~~`menu.popup()` 阻塞是"本库差异"~~ | ~~`await popup()` 之后用户已选完~~ | **归类有误**：muda 在 Windows 走同步 `TrackPopupMenu`、macOS 走 `popUpMenuPositioningItem`，Tauri 的主线程同样被阻塞。见 §5.2 |
| 8 | `Image.close()` 是**补壳** | 调用不报错、无副作用，debug 模式打警告 | B14 决策，零删改优先 |
| 9 | 内嵌资源 origin 是 `oriel://<host>` | 依赖 `location.origin` 的前端行为不同；`tauri://localhost` 不存在 | 有意；`convertFileSrc` 固定 `oriel://file.oriel/` |
| 10 | `Channel` 无 index，不保证重排 | 高并发流式推送可能乱序 | 有意取舍（API.md §11.3） |

### 5.1 `__TAURI_INTERNALS__`：为什么不能给兼容标记，只能静态查

它不能靠运行时 shim 解决，原因是**逻辑上的**，不是"懒得做"：

- `"__TAURI_INTERNALS__" in window` 要的是 `false`（本库没有这个对象），
  而"检测到有人探测它"要的是**能观察到这次读取**。`in` 运算符无法拦截，
  `defineProperty` 一挂上去 `in` 就变 `true`——两个目标互斥。
- 挂个空对象更糟：探测通过、调用 `.transformCallback` 即炸，故障点从"启动时静默降级"
  变成"运行到某个分支时崩"，更难查。

所以正确的处理是**在源码层把它找出来**：`tools/check-tauri-leaks.mjs` 扫描迁移项目，
把 `__TAURI_INTERNALS__`、`plugin:` 命令名、`tauri://` 事件名、`@tauri-apps/*` 导入
逐条列出来并给出改法。这些字符串在源码里可见，静态检查的查全率是 100%。

### 5.2 `menu.popup()`：是平台事实，不是本库与 Tauri 的差异

查了上游实现：Tauri 的 `popup_inner` 最终调 muda 的 `show_context_menu_for_hwnd`（Windows）
与 `show_context_menu_for_nsview`（macOS），前者是同步的 `TrackPopupMenu`、后者是同步的
`popUpMenuPositioningItem:`。两边的**主线程**都会被原生菜单阻塞到用户选择为止。

差别只在 Promise 的**状态机**：Tauri 把显示动作丢进主线程队列后立即 resolve，本库阻塞到菜单关闭。
但"resolve 之后的代码"同样要等主线程空出来，所以**可观察行为一致**。

真正该记的是这条：**别用 `await popup()` 判断用户选了什么**，可靠信号是 `menu.itemclicked`。
三平台本来就不同（Linux 的 GTK 菜单是异步的），拿返回时机当契约在哪个库里都会错。

另外三条不那么常见但会咬人：

- **`getTauriVersion()` 返回的是库版本**（`0.5.0`），不是框架版本。任何版本号比较都要重写。
- **`event.emit` 不默认放行**（Tauri 里 emit 是普通 API）。它让一个窗口驱动另一个窗口的行为，
  要显式 `Allow("event.emit")`。
- **`onAction` 订阅时抛 `not_supported`**——这一条其实**是对齐的**：Tauri 的 Actions API
  官方标注 "only available on mobile platforms"，桌面端本来就不工作。

## 6. 第五层：定位差异（不是缺口，别当成待办）

| 维度 | Tauri 2 | OrielWeb |
|---|---|---|
| 宿主语言 | Rust（+ `wry`/`tao`/`winit`） | **纯 C# P/Invoke，无 C++/Rust 中间层** |
| IPC | serde + 命令宏 + 运行时路由 | 源生成器编译期路由、零反射；实测 1000 条路由与 1 条同耗时（1.19 μs vs 1.24 μs） |
| 发布形态 | 各平台原生二进制 | Native AOT 单文件；demo 实测 6.1 MB（含内嵌前端资源） |
| 前端资源 | 打进二进制，经 `tauri://localhost` 应答 | 编译进程序集，经 `oriel://<host>` 直答，**不落盘、也不解压到任何目录** |
| 生态 | npm + crates.io，第三方插件可发布 | NuGet + npm，**无插件生态** |
| 定位 | 应用框架 / 平台 | **核心库**（webview 宿主 + IPC + 平台集成） |

体积那一行只写了实测值，没有 Tauri 侧的对照——没有同机同配置的实测，不做"更小/更大"的断言。

## 7. 本次核对抓出的三处"说法与事实不符"

对比的意义一半在于查自己。这三处都不是实现错，是**账本与文档错了**：

1. **`notification` 的 17 条基线里有 2 条是幽灵。** `GAPS.notification` 列了
   `deleteChannel` / `listChannels`，而 `@tauri-apps/plugin-notification@2.12.4` 的运行期
   导出面里**没有这两个名字**（已被 `channels()` 取代）。缺口真值是 **15 不是 17**。
2. **"`Importance`/`Visibility` 是纯类型别名、Tauri 不挂在运行期导出面"是错的。**
   实测这两个名字就在 `Object.keys()` 里（Tauri 文档的示例也直接 `import` 它们）。
   所以 notification 的缺口 6 不是"口径差异"，就是实打实的 6 条。
3. **`docs/API.md` 与 `src/image.js` 顶部注释还说 `Image` 没有 `close()`、调用会抛
   `TypeError`。** B14 起已有补壳 `close()`（`src/image.js:293`，debug 打警告）。文档落后于实现。

**账本缺一条断言**：现在只检查"GAPS 里列着但我们已经实现"，不检查"GAPS 里列着但**参照实现
也没有**"。少了这个方向，Tauri 删掉的 API 会永远留在我们的缺口清单里，而总数看起来一直很合理。

## 8. 从"能不能迁"看，还剩多少

| 应用类型 | 结论 |
|---|---|
| 单窗口工具（dialog + fs + clipboard + opener + 自定义命令） | **可迁，零删改**。B24 演练 24 个导入符号缺口 3 → 0 |
| 多窗口 / 停靠面板 | **可迁**。`window.new` + `webviewWindow` 已补；嵌套 webview 要改架构 |
| 托盘 / 菜单密集 | **可迁**。`api/tray` 形状对齐，`TrayIcon` 类可用 |
| 依赖 `window-state` / `store` / `global-shortcut` | **需额外工作**。前两个建议库内补，第三个按需自建 |
| 依赖 `updater` | **需额外工作**。Velopack 打包已通，接 `UpdateManager` 即可 |
| 依赖第三方 Tauri 插件 | **迁不了**。没有插件机制，只能重写 |
| 依赖 `sql` / `stronghold` / `http` / `websocket` | **不改架构迁不了**，要么换实现，要么自己写命令 |
| 移动端应用 | **不适用** |

## 9. 建议的下一批（按"真实撞击 × 成本"排）

页面 API 面已经没有值得做的了（15 条全是不该做的）。下一批应当全部落在生态与工程链路上：

1. **`window-state`（库内）**——三平台都不用写原生代码，存尺寸/位置/最大化即可。
   几乎所有桌面应用都需要，**收益最高、成本最低**。
2. **Velopack 应用侧更新**——`Main` 首行 `VelopackApp.Build().Run()` + `UpdateManager` 封装。
   打包已通，只差这一步；不做的话所有带更新入口的应用都得自己写。
3. **`store`（库内）**——JSON 键值存储，`fs` 已够用，包一层即可。
4. **`process.relaunch` + `plugin-os`**——薄，`Environment` + `Process.Start` 就够。
5. **账本补两条断言**（半小时）：GAPS 条目在参照实现里是否仍存在；`EXPECTED_GAPS` 的
   notification 组按实测改成 6 条。
6. **单实例通知载荷**——`TryNotifyPrimary` / `ListenAsync` 已经留了位置，只是 `OrielApp`
   传了空串。补上就能支持"第二次启动带文件路径在已有窗口打开"。

不建议做：`webview` 模块、移动端、`http`/`websocket`/`sql`/`stronghold`、CSP 注入与隔离模式
（要动三平台响应头与脚本注入，收益取决于威胁模型，需先定策略）。
